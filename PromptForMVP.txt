**Контекст проекта:**
Разрабатывается MVP модуля для клиринговой системы по обработке сделок РЕПО. Сделка РЕПО состоит из двух частей: Leg 1 (открытие) и Leg 2 (закрытие с уплатой процентов). На данном этапе реализуется только режим ночной пакетной загрузки данных из Торговой системы. Весь остальной функционал (realtime, обработка дефолтов) вынесен в Этап 2.

### **Задача: Разработать MVP Модуля обработки сделок РЕПО**

На основе финальной версии ТЗ (`TZ_REPO_module_v1_11052026.docx`) реализуй следующую функциональность и архитектуру.

**0. Демо-режим на SQLite (СКВОЗНОЕ ТРЕБОВАНИЕ)**

Модуль должен поддерживать два режима работы, переключаемых через конфигурацию:

- **Продакшн-режим:** PostgreSQL 15+, Kafka, SFTP/S3 для загрузки файлов.
- **Демо-режим:** SQLite, файловая система вместо SFTP/S3, логирование в stdout/файл вместо Kafka.

Требования к демо-режиму:

- **Единый запуск:** Вся система (API, batch-обработчик, БД) должна запускаться одной командой (например, `make demo` или `docker-compose up demo`).
- **Генерация синтетических данных:** Реализуй скрипт-генератор (`scripts/generate_demo_data.py`), который создает:
  - `instruments.json` — список из 15-20 инструментов (ISIN, разные валюты, ставки day_count_convention).
  - `participants.json` — список из 10 участников.
  - `sod_balances.json` — начальные остатки (SOD) на 3 торговых дня для всех участников по всем инструментам и деньгам (остатки должны быть достаточны для исполнения сделок без REJECTED).
  - Файл сделок за каждый день (`trades_2026-05-07.jsonl`, `trades_2026-05-08.jsonl`, `trades_2026-05-10.jsonl`) по 50-100 сделок в каждом, покрывающих сценарии:
    - Разные роли (с `initiator_role` и без — для демонстрации fallback).
    - Разные даты maturity (от 1 до 14 дней).
    - Разные ставки и инструменты.
    - Граничные случаи (одна сделка с неизвестным инструментом → REJECTED; к концу 3-го дня — сделка, которая должна упасть в INSUFFICIENT_BALANCE, так как в файле генератора специально не хватит остатка).
- **Полная автономность:** Демо-режим не требует внешних зависимостей (Kafka, SFTP-сервер). Загрузка файла эмулируется чтением из директории `demo_data/incoming/`.
- **Идентичная бизнес-логика:** Все операции (валидация, chunked processing, SAVEPOINT-логика, pre-check, CHECK-ограничение, расчет позиций) выполняются точно так же, как в продакшене. Отличие — только диалект SQL и источник данных.
- **Адаптация DDL:** Предоставь отдельный набор миграций/схем для SQLite, учитывая его ограничения:
  - `DECIMAL(20,6)` → `REAL` (с контролем точности через ROUND в коде).
  - `UUID` → `TEXT`.
  - Партиционирование и `CHECK`-ограничения — эмулируются триггерами `BEFORE INSERT` или логикой в коде.
  - `gen_random_uuid()` → `hex(randomblob(16))` или генерация на стороне приложения.

**Сценарий демонстрации:**

При запуске демо-режима система должна выполнить:
1. Создать/мигрировать схему БД SQLite.
2. Загрузить справочники (`instruments`, `participants`).
3. Загрузить `sod_balances` за 2026-05-07.
4. Загрузить файл `trades_2026-05-07.jsonl` в пакетном режиме, выполнить EOD-расчет, вывести `load_report` в консоль.
5. Повторить шаги 3-4 для 2026-05-08 и 2026-05-10 (последовательно).
6. После обработки всех дней:
   - Вывести в консоль итоговую статистику: `COMMITTED: X, REJECTED: Y, DUPLICATES: Z, FAILED_CHUNKS: W`.
   - Выполнить серию GET-запросов к REST API для демонстрации:
     - Позиции участника `BANK_A` на 2026-05-10.
     - Future Obligations участника `BANK_B` с 2026-05-08 по 2026-05-20.
     - Получить `load_report` за 2026-05-10.
     - Попытка отменить сделку в статусе ACTIVE (ожидается 409 Conflict).
   - Сгенерировать EOD Position Report (CSV) в `demo_data/out/eod_report_2026-05-10.csv`.

Ожидаемый результат демо: в консоль выводится читаемая последовательность шагов с ключевыми метриками, а в выходной директории сохраняются сформированные отчеты.

**1. Основная функциональность (MVP Scope)**
Реализуй строго в рамках Этапа 1, не забегая в Roadmap:
- **Пакетная обработка:** Реализуй единственный метод загрузки — ночной Batch. Входной файл (JSON Lines, UTF-8) забирается по SFTP или из S3-совместимого хранилища (в демо — из локальной директории). Realtime и ручной ввод через REST не реализовывать.
- **Маппинг ролей:** На входе есть нейтральные `party_1`, `party_2` и опциональное поле `initiator_role` (`SECURITY_SELLER` или `SECURITY_BUYER`). Реализуй логику маппинга на `participant_id` (продавец бумаг / заёмщик денег) и `counterparty_id` (покупатель бумаг / кредитор). Если `initiator_role` отсутствует, примени критичный fallback (см. п. 3.1.2 ТЗ), где `party_1` по умолчанию считается `SECURITY_SELLER`, с обязательным логированием WARNING.
- **Расчет T+0:** Дата расчетов по первой части (`leg1_settlement_date`) всегда равна дате сделки (`trade_date`). При ночной загрузке статус сделки сразу становится `ACTIVE` (минуя `NEW`), и проводки по Leg 1 применяются немедленно.
- **Расчет Leg 2:** Реализуй расчет `Leg2_Amount` по формуле:
  `Repo_Income = ROUND(leg1_amount * rate * Days / 365, 2, HALF_UP)`
  `Leg2_Amount = ROUND(leg1_amount + Repo_Income, 2, HALF_UP)`
  Где `Days = leg2_settlement_date - leg1_settlement_date`. Конвенция округления — **строго математическая (half-up)**.
- **Позиции (EOD):** Введи сущность `positions` с единым полем `balance` и классификатором `balance_type` (`SECURITIES` или `CASH`). Для денег `instrument_id` = `CASH_{currency}`. При сохранении гарантируй целостность через прикладной `pre-check` и `CHECK (balance >= 0)` на уровне БД (в SQLite — через триггер BEFORE INSERT/UPDATE с вызовом `RAISE(ABORT, ...)`).
- **Future Obligations:** При регистрации сделки создавай записи в реестре будущих обязательств на дату `leg2_settlement_date`.
- **API:** Реализуй минимальное REST API только для чтения (`GET /trades`, `GET /positions`, `GET /obligations`, `GET /reports`), отмены сделки в статусе NEW (`DELETE /trades/{id}`) и ручного запуска загрузки (`POST /batch/load`).

**2. Ключевые архитектурные решения (v4.0)**
Эти пункты критически важны для приемки MVP:
- **Chunked Processing с SAVEPOINT:** НЕ используй одну гигантскую транзакцию на весь файл. Обрабатывай файл чанками (по умолчанию 1000 записей). Внутри чанка:
    - Для **бизнес-ошибок** (невалидные данные, нераспознанная роль, недостаточный баланс на pre-check) используй `SAVEPOINT` перед каждой записью. При ошибке откатывайся к точке сохранения, фиксируй запись в `rejected_trades`, и **продолжай обработку чанка**.
    - Для **системных ошибок** (IO, нарушение CHECK-ограничения БД) откатывай (`ROLLBACK`) **весь чанк** и пробуй заново до 3 раз. При неудаче чанк пропускается, инкрементируется счетчик `failed_chunks`.
    - В SQLite `SAVEPOINT` поддерживается нативно — используй тот же код, что и для PostgreSQL.
- **Эшелонированная защита:** Перед любой проводкой выполняй `pre-check` в коде. На уровне БД поле `positions.balance` должно иметь ограничение `CONSTRAINT chk_positive_balance CHECK (balance >= 0)`. Его срабатывание — это критический алерт, означающий баг.
- **Допущение о фантомных позициях:** В MVP Leg 1 считается исполненным в момент успешной регистрации сделки (прохождение pre-check, статус `ACTIVE`). Не реализовывай ожидание подтверждения от Расчетной системы. Сверка будет ручной (см. риск R8).
- **Аудит и идемпотентность:** Все операции фиксируй в `position_audit_log` (append-only с hash-цепочкой SHA-256). Входящие сообщения сохраняй в `raw_trades`. Дедупликация — по `idempotency_key` (хранение 30 дней в партиционированной таблице; для SQLite — отдельная таблица с TTL-очисткой).

**3. Модель данных (DDL)**
Создай миграции для следующих таблиц в PostgreSQL 15+:
- `raw_trades`: партиционированная по `received_at`.
- `trades`.
- `positions` (c `UNIQUE(participant_id, instrument_id, balance_type, position_date, status)`).
- `future_obligations`.
- `instruments`.
- `position_audit_log`.
- `rejected_trades`.
- `load_reports` (c `UNIQUE(eod_date)`).

А также отдельный набор DDL для SQLite, учитывающий его ограничения (см. пункт 0).

**4. Тестирование**
Подготовь каркас для следующих тестов (`pytest`/`JUnit`):
- Unit-тесты на формулу расчета Leg2 и маппинг ролей с fallback.
- Интеграционные тесты на chunked-обработку с изоляцией ошибок (валидные данные не должны теряться из-за одного rejected).
- Тест на срабатывание CHECK-ограничения БД при прямой вставке отрицательного баланса.
- Тест на идемпотентность повторной загрузки файла.
- **End-to-end тест демо-режима:** Полный прогон сгенерированных данных за 3 дня с проверкой итоговых позиций и отчетов.
- Тест на идентичность результатов между PostgreSQL и SQLite на одинаковых входных данных.
